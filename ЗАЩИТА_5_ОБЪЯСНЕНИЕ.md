## 1. Что требуется в задании (расшифровка)

Задание состоит из пяти последовательных шагов. Каждый следующий шаг
модифицирует предыдущий, поэтому итоговый проект содержит результат всех пяти.

| Пункт | Требование | Что это значит на практике |
|---|---|---|
| **5.I** | Для «обычной» и модифицированной (с рандомом) функций, в своих пространствах имён, для типа `int` подготовить файлы и собрать проект через CMake. Реализацию оформить как **библиотеку**, исходники лежат **в одной директории с `main`**. | Два `.h` + два `.cpp` + `main.cpp` + `CMakeLists.txt` в одной папке. `add_library(mylib STATIC ...)`, затем `target_link_libraries`. |
| **5.II** | Модифицировать: библиотека — в **отдельной поддиректории**. | Появляется папка `my_lib/` со своим `CMakeLists.txt`; в корневом — `add_subdirectory(my_lib)`. |
| **5.III** | Подключить **googletest**, тесты — в отдельной директории. Написать тесты, показать успешную сборку и выполнение. Сделать тест(ы) провальными и показать результат. Показать разницу `ASSERT_` и `EXPECT_`. | Папка `tests/`, `FetchContent` для gtest, `gtest_discover_tests`. Один тест намеренно падает. |
| **5.IV** | Можно **включать/выключать сборку тестов** (опция). | `option(BUILD_TESTS ... ON)` + `if(BUILD_TESTS) add_subdirectory(tests) endif()`. |
| **5.V** | Заменить функции в библиотеке на **шаблонные**. | `template<typename T> double hypotenuse(T a, T b)` в заголовке; библиотека становится header-only (`INTERFACE`). |

Важно из формулировки 5.I: **нельзя** создавать проект средствами IDE и нельзя
запускать/собирать через IDE. То есть терминал:

```bash
cmake -S . -B build
cmake --build build
ctest --test-dir build
./build/exec_trg
```

Редактор (VS Code) использовать можно, а кнопки «Run/Build» в IDE — нет.

## 3. Как в C++ устроены заголовки и библиотеки (база, без которой не объяснить)

### 3.1. Единица трансляции

Компилятор обрабатывает каждый `.cpp` отдельно. Сначала **препроцессор**
вставляет содержимое всех `#include` прямо в текст файла — получается
**единица трансляции** (translation unit). Затем она компилируется в объектный
файл `.o`, и в конце **компоновщик** (linker) склеивает объектные файлы в
исполняемый файл.

```
main.cpp ─┐
          ├─ препроцессор → компилятор → .o ─┐
lib.cpp  ─┘                                  ├─ linker → a.out
                          libmylib.a ────────┘
```

### 3.2. Заголовок `.h` и файл `.cpp`

- `.h` — **объявление** (declaration): «такая функция существует, вот её
  сигнатура». Компилятору этого достаточно, чтобы проверить вызов.
- `.cpp` — **определение** (definition): тело функции, то есть код.

Если объявление есть, а определения нигде нет — программа компилируется, но
падает на компоновке с ошибкой `undefined reference to ...`.

`#pragma once` в начале заголовка — защита от повторного включения одного и
того же файла в рамках одной единицы трансляции (иначе класс/функция окажутся
объявлены дважды).

### 3.3. Что такое «подключить как библиотеку»

Это не «скопировать код в main», а:

1. собрать отдельную **цель** (`add_library`);
2. подключить её к исполняемому файлу (`target_link_libraries`).

CMake тогда сам передаёт компоновщику нужный архив/флаг и **пробрасывает
требования использования** (usage requirements) — например, каталоги
заголовков. Именно поэтому в `tests/my_test.cpp` можно писать
`#include "hypotenuse.h"`, хотя тест лежит в другой папке: CMake добавил
`-I.../my_lib` (см. `build/tests/CMakeFiles/mytst_exec.dir/flags.make`).

## 4. Разбор файлов решения

### 4.1. `my_lib/hypotenuse.h` — «обычная» функция

```cpp
#pragma once
#include <cmath>

namespace my_lib {
    namespace usual {
        template<typename T>
        double hypotenuse(T a, T b) {
            return std::sqrt(static_cast<double>(a)*a + static_cast<double>(b)*b);
        }
    }
}
```

Что здесь важно:

- **`#pragma once`** — заголовок можно включать много раз.
- **`#include <cmath>`** — нужен для `std::sqrt`.
- **Пространства имён** `my_lib::usual` — чтобы функция не конфликтовала с
  чужими `hypotenuse` из других библиотек. Имя `my_lib` — «фамилия» вашей
  библиотеки, `usual` — версия функции. В C++17 то же самое можно записать
  короче: `namespace my_lib::usual { ... }`.
- **`template<typename T>`** — это и есть 5.V. `T` — параметр-тип; компилятор
  создаёт отдельную версию функции для каждого типа, с которым её вызвали
  (`<int>`, `<double>`, `<long>` и т.д.). Это называется **инстанцированием**
  шаблона, и оно происходит **на этапе компиляции**.
- **`static_cast<double>(a) * a`** — приведение к `double` до умножения. Если
  перемножить два больших `int`, результат может переполниться (`int` обычно
  32 бита). Приведение делает арифметику вещественной и заодно даёт точный
  `sqrt`.
- **Возврат `double`**, потому что корень из целого почти всегда не целый.
- Формула: гипотенуза = √(a² + b²) — теорема Пифагора.

### 4.2. `my_lib/hypotenuse_rand.h` — версия с рандомом

```cpp
#pragma once
#include <cmath>
#include <random>

namespace my_lib {
    namespace randver {
        template<typename T>
        double hypotenuse_rand(T a, T b) {
            double res = std::sqrt(static_cast<double>(a)*a + static_cast<double>(b)*b);
            static std::mt19937 gen(std::random_device{}());
            std::uniform_int_distribution<int> coin(0, 1), add(0, 10);
            if (coin(gen)) res += add(gen);
            return res;
        }
    }
}
```

- `std::random_device` — источник «настоящей» случайности (обычно из ОС). Им
  **один раз** инициализируют генератор.
- `std::mt19937` — генератор псевдослучайных чисел (вихрь Мерсенна, 32 бита).
  `static` означает: объект создаётся один раз при первом вызове и живёт до
  конца программы. Это дешевле, чем создавать и заново засевать генератор на
  каждом вызове.
- `std::uniform_int_distribution<int> coin(0, 1)` — равномерно выдаёт 0 или 1
  (бросок монетки). `add(0, 10)` — равномерно целое от 0 до 10.
- Логика: с вероятностью 50 % к «настоящей» гипотенузе прибавляется случайное
  число 0..10. Итог всегда в диапазоне `[hypot, hypot + 10]`.
- Зачем это вообще: «модифицированная» функция должна вести себя
  непредсказуемо, чтобы показать, что тестировать её можно только по
  **диапазону**, а не по одному значению.

> Тонкость: `static std::mt19937` не потокобезопасен, и в тестах результат
> нельзя предсказать. Это нормально для учебной демонстрации, но на защите
> стоит сказать, что для воспроизводимых тестов генератор обычно засевают
> фиксированным числом (`std::mt19937 gen(42);`).

### 4.3. `5.all.cpp` — программа

```cpp
#include <iostream>
#include "hypotenuse.h"
#include "hypotenuse_rand.h"

int main() {
    int a, b;
    std::cin >> a >> b;
    std::cout << my_lib::usual::hypotenuse(a, b) << "\n";
    std::cout << my_lib::randver::hypotenuse_rand(a, b) << "\n";
    return 0;
}
```

- Кавычки в `#include "..."` — «искать сначала рядом с исходником и в
  каталогах, добавленных через `-I`» (для своих заголовков). Угловые скобки
  `<...>` — для системных/внешних.
- `T` выводится автоматически из аргументов `int`, поэтому `<int>` писать не
  обязательно.
- Вывод: гипотенуза и «гипотенуза + возможно 0..10».

### 4.4. `my_lib/CMakeLists.txt` — библиотека

```cmake
add_library(mylib INTERFACE)
target_include_directories(mylib INTERFACE ${CMAKE_CURRENT_SOURCE_DIR})
```

Это ответ на 5.V. Раз библиотека теперь состоит только из шаблонов в
заголовках:

- `INTERFACE` — у цели **нет** своих объектных файлов и архива `.a`. Это
  «набор требований использования»: «кто на меня ссылается — добавь себе этот
  include-каталог».
- `target_include_directories(... INTERFACE ...)` — каталог нужен
  **потребителям** (`exec_trg`, `mytst_exec`), а самой цели собирать нечего.
- `CMAKE_CURRENT_SOURCE_DIR` — папка, где лежит **этот** `CMakeLists.txt`
  (то есть `5lesson/my_lib`). Не путать с `CMAKE_SOURCE_DIR` — это корень
  всего проекта.

Почему шаблоны обязаны быть в заголовке: компилятор генерирует код функции
для каждого `T` **в том файле, где встретил вызов**. Если тело шаблона
спрятать в `.cpp`, то `5.all.cpp` увидит только объявление, сгенерировать
код не сможет — будет ошибка компоновки. Есть и альтернативы (явное
инстанцирование, `.tpp`), но header-only — самый обычный вариант.

**Как выглядели 5.I/5.II (до шаблонов).** Тогда функции были обычными, для
`int`, и библиотека была настоящей статической:

```cmake
add_library(mylib STATIC hypotenuse.cpp hypotenuse_rand.cpp)
target_include_directories(mylib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

После сборки появлялся файл `build/libmylib.a`. В 5.I эти файлы лежали рядом с
`main`, в 5.II — переехали в `my_lib/`. На защите стоит уметь показать эту
разницу: «сначала был `STATIC` и `.a`, после 5.V — `INTERFACE`, потому что
шаблоны».

### 4.5. Корневой `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.14 FATAL_ERROR)   # минимальная версия CMake
project(test_proj VERSION 0.0.0 LANGUAGES CXX)     # имя проекта, язык C++

set(CMAKE_CXX_STANDARD 17)           # стандарт C++17
set(CMAKE_CXX_STANDARD_REQUIRED ON)  # не откатываться на старый стандарт

option(BUILD_TESTS "Build tests" ON) # 5.IV: опция, по умолчанию ON

add_subdirectory(my_lib)             # 5.II: зайти в поддиректорию библиотеки

add_executable(exec_trg 5.all.cpp)   # исполняемый файл из main
target_link_libraries(exec_trg PUBLIC mylib)  # подключить библиотеку

if(BUILD_TESTS)                      # 5.IV: тесты только если включены
    add_subdirectory(tests)
endif()
```

Пояснения:

- `cmake_minimum_required` задаёт минимальную версию CMake и политики
  совместимости. `FATAL_ERROR` — устаревший «модификатор» (с CMake 3.0 он
  игнорируется, ошибка и так фатальна), на работу не влияет.
- `project(... LANGUAGES CXX)` включает только C++; `VERSION` — метаданные.
- `CMAKE_CXX_STANDARD 17` + `REQUIRED ON` дают флаг `-std=gnu++17` (GNU-
  расширения включены по умолчанию; строго `-std=c++17` было бы при
  `set(CMAKE_CXX_EXTENSIONS OFF)`).
- `option` создаёт **кэшированную** логическую переменную. Значение можно
  переопределить из командной строки: `-DBUILD_TESTS=OFF`. `if(BUILD_TESTS)`
  проверяет её истинность.
- `add_subdirectory` — «выполнить CMake-сценарий из подпапки», он создаёт
  цели, объявленные там.
- `target_link_libraries(exec_trg PUBLIC mylib)`:
  - для исполняемого файла достаточно `PRIVATE` (он никому не передаёт свои
    требования). `PUBLIC` здесь не ошибка, но избыточно;
  - ключевое: линкуется **цель**, а не путь к файлу. CMake сам разберётся,
    что передать компоновщику, и пробросит include-каталоги.

Строка

```cmake
set_source_files_properties(5.all.cpp PROPERTIES LANGUAGE CXX)
```

не нужна: расширение `.cpp` уже означает C++. Она безвредна, но
преподаватель может спросить «зачем» — честный ответ: «осталась от
экспериментов, можно удалить».

### 4.6. `tests/CMakeLists.txt`

```cmake
include(FetchContent)
FetchContent_Declare(
    googletest
    URL https://github.com/google/googletest/archive/5376968f6948923e2411081fd9372e71a59d8e77.zip
)
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(googletest)

enable_testing()

add_executable(mytst_exec my_test.cpp)
target_link_libraries(mytst_exec PUBLIC GTest::gtest_main)
target_link_libraries(mytst_exec PUBLIC mylib)
target_include_directories(mytst_exec PUBLIC ${CMAKE_SOURCE_DIR}/my_lib)

include(GoogleTest)
gtest_discover_tests(mytst_exec)
```

- `FetchContent` — механизм CMake, который **на этапе конфигурации** скачивает
  зависимость (здесь — архив googletest по фиксированному коммиту
  `5376968f...`) в `build/_deps/`, распаковывает и добавляет как
  подпроект. Плюс: не нужно ничего устанавливать в систему, версия
  зафиксирована. Минус: нужен интернет при первой конфигурации.
- `gtest_force_shared_crt` — настройка для MSVC (Windows), на macOS/Linux
  ни на что не влияет. Можно объяснить так: «стандартная рекомендация из
  документации googletest, чтобы не было конфликта рантаймов».
- `GTest::gtest_main` — цель, которая содержит и сам gtest, и готовый
  `main()`. Поэтому в `my_test.cpp` **нет** `int main()` — тестовый фреймворк
  предоставляет его сам.
- `target_link_libraries(mytst_exec PUBLIC mylib)` — тесты видят заголовки
  библиотеки. Строка
  `target_include_directories(mytst_exec PUBLIC ${CMAKE_SOURCE_DIR}/my_lib)`
  после этого **дублирует** то, что уже пробрасывает `mylib`, и написана
  через `PUBLIC` вместо `PRIVATE`. Лучше удалить (или заменить на
  `PRIVATE`, но и тогда она не нужна).
- `enable_testing()` включает CTest в текущем каталоге и ниже. Если её
  убрать, `ctest` не увидит тесты.
- `gtest_discover_tests(mytst_exec)` — на этапе **сборки** запускает
  `mytst_exec --gtest_list_tests`, получает список тестов и регистрирует
  каждый `TEST` как **отдельный** тест CTest. Поэтому `ctest` показывает
  `1/4 ... 4/4`, а не «один бинарник».

### 4.7. `tests/my_test.cpp`

```cpp
#include "hypotenuse.h"
#include "hypotenuse_rand.h"
#include <gtest/gtest.h>

TEST(HypotenuseSuite, TestNormal) {
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 5.0);
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(6, 8), 10.0);
}

TEST(HypotenuseSuite, TestZero) {
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(0, 0), 0.0);
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(0, 5), 5.0);
}

TEST(HypotenuseSuite, AssertVsExpect) {
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 5.0);   // ok
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 99.0);  // падает, идём дальше
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 5.0);   // ok

    ASSERT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 5.0);   // ok
    ASSERT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 99.0);  // падает, тест прерывается
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<int>(3, 4), 5.0);   // НЕ выполнится
}

TEST(HypotenuseRandSuite, TestRange) {
    for (int i = 0; i < 100; ++i) {
        double v = my_lib::randver::hypotenuse_rand<int>(3, 4);
        EXPECT_GE(v, 5.0);   // >= 5
        EXPECT_LE(v, 15.0);  // <= 15
    }
}
```

- `TEST(Набор, Имя)` разворачивается в класс-наследник `::testing::Test`;
  тело — в метод `TestBody()`. «Набор» (suite) — группировка тестов.
- `EXPECT_*` — **нефатальная** проверка: при провале печатает ошибку и
  выполняет следующие строки. `ASSERT_*` — **фатальная**: при провале
  делает `return` из текущего теста, остаток теста не выполняется (программа
  при этом не падает и другие тесты идут).
- `_DOUBLE_EQ` сравнивает не «в лоб» через `==`, а с допуском (около 4 ULP):
  два вещественных числа, полученных разными формулами, могут отличаться в
  последнем бите. Для явного допуска есть `EXPECT_NEAR(a, b, eps)`.
- `EXPECT_GE` / `EXPECT_LE` — «greater or equal» / «less or equal».

**Что реально печатает бинарник** (проверено на вашем проекте):

```
[ RUN      ] HypotenuseSuite.TestNormal
[       OK ] HypotenuseSuite.TestNormal (0 ms)
...
[ RUN      ] HypotenuseSuite.AssertVsExpect
my_test.cpp:17: Failure
Expected equality of these values:
  my_lib::usual::hypotenuse<int>(3, 4)
    Which is: 5
  99.0
    Which is: 99
my_test.cpp:21: Failure
...
[  FAILED  ] HypotenuseSuite.AssertVsExpect (0 ms)
...
[  PASSED  ] 3 tests.
[  FAILED  ] 1 test
```

Обратите внимание: ошибок **две** (строки 17 и 21), хотя неправильных
проверок три. Строка 18 «упала бы»? Нет — она верна (5 == 5), поэтому ничего
не печатается. Строка 22 не выполнилась вообще, потому что `ASSERT` на
строке 21 прервал тест. Это и есть демонстрация разницы.

## 5. Полная сборка и запуск (что и зачем)

### 5.1. С нуля

```bash
cd 5lesson
rm -rf build                 # чистая сборка
cmake -S . -B build          # конфигурация: прочитать CMakeLists, скачать gtest
cmake --build build          # сборка (можно -j4 для параллельности)
ctest --test-dir build --output-on-failure   # запуск тестов через CTest
./build/exec_trg             # демонстрационная программа
```

`-S .` — каталог с исходниками (source), `-B build` — каталог сборки (build).
Это **out-of-source build**: все сгенерированные файлы лежат отдельно и не
мусорят исходники; `build` можно удалить и пересобрать.

`ctest --output-on-failure` печатает вывод теста только если тот упал — так
удобнее показывать.

### 5.2. Запуск одного теста / только зелёных

```bash
ctest --test-dir build -R HypotenuseSuite.TestNormal   # по имени (регулярка)
ctest --test-dir build -E AssertVsExpect               # исключить намеренно падающий
./build/tests/mytst_exec --gtest_filter=HypotenuseSuite.*
./build/tests/mytst_exec --gtest_filter=-*AssertVsExpect*
```

### 5.3. Демонстрация 5.IV (выключение тестов)

```bash
cmake -S . -B build-no-tests -DBUILD_TESTS=OFF
cmake --build build-no-tests
```

Что проверить на защите:

- в конфигурации **не** скачивается googletest (нет `build-no-tests/_deps`);
- в списке целей нет `mytst_exec`, `gtest`, `gmock` — только `exec_trg`;
- программа работает как обычно.

А `-DBUILD_TESTS=ON` (или просто без флага, так как по умолчанию `ON`)
возвращает тесты. Значение кэшируется в `build/CMakeCache.txt`, поэтому
менять его лучше на чистом каталоге сборки или с `-U BUILD_TESTS`.

## 6. Слабые места проекта и как на них отвечать

Это не «ошибки, за которые отчислят», но преподаватель может зацепиться.
Лучше знать заранее.

### 6.1. `ctest` из корня не видит тесты (важно!)

Сейчас `enable_testing()` вызывается только в `tests/CMakeLists.txt`, поэтому
файл `CTestTestfile.cmake` создаётся только в `build/tests/`. В результате:

```
$ ctest --test-dir build
No tests were found!!!
```

а работает только

```
$ ctest --test-dir build/tests
```

**Исправление** — добавить `enable_testing()` в корневой `CMakeLists.txt`
(до `add_subdirectory`, рядом с `option`). Проверено: после этого
`ctest --test-dir build` находит все 4 теста.

Либо `include(CTest)`, который сам вызывает `enable_testing()` и добавляет
цель `Experimental`.

Как отвечать, если ещё не исправлено: «CTest включён в поддиректории тестов,
поэтому запускать нужно `ctest --test-dir build/tests`; чтобы работал запуск из
корня, `enable_testing()` надо перенести в корневой CMakeLists».

### 6.2. Намеренно падающий тест делает весь прогон красным

Это требование 5.III («сделать тест провальным и продемонстрировать»), так что
это нормально. Но 5.III требует ещё и «продемонстрировать выполнение тестов»
(успешное). Поэтому показывайте так:

```bash
ctest --test-dir build/tests                     # 75%, 1 намеренно упал
ctest --test-dir build/tests -E AssertVsExpect   # 100% зелёные
```

И объясняйте: «тест `AssertVsExpect` — учебный стенд для разницы ASSERT/EXPECT,
он падает специально».

### 6.3. Библиотеки «нет» — только `INTERFACE`

Вопрос: «Где сама библиотека? Почему нет `libmylib.a`?» Ответ: после 5.V
функции стали шаблонными, а шаблоны обязаны быть в заголовках; поэтому
библиотека header-only, и CMake-цель типа `INTERFACE` только пробрасывает
include-каталог. В 5.I/5.II была цель `STATIC` и файл `libmylib.a` — это можно
показать отдельной сборкой (см. раздел 7).

### 6.4. Лишние строки

- `set_source_files_properties(5.all.cpp PROPERTIES LANGUAGE CXX)` — не нужна;
- `target_include_directories(mytst_exec PUBLIC ${CMAKE_SOURCE_DIR}/my_lib)` —
  дублирует проброс от `mylib`, и `PUBLIC` у исполняемого файла не имеет
  смысла; лучше `PRIVATE` или удалить;
- `FATAL_ERROR` в `cmake_minimum_required` устарел.

Честный ответ: «это избыточные/учебные строки, на сборку не влияют; убрать
можно».

### 6.5. Тесты только для `int`

5.V требует шаблонные функции, а тесты проверяют только `<int>`. Хорошо бы
показать, что шаблон работает и для `double`:

```cpp
TEST(HypotenuseSuite, DoubleType) {
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<double>(3.0, 4.0), 5.0);
    EXPECT_DOUBLE_EQ(my_lib::usual::hypotenuse<double>(1.5, 2.0), 2.5);
}
```

(3-4-5 и 1.5-2-2.5 — «египетские» тройки, красивые проверки.)

### 6.6. `build/` в git

Каталог `build` с сотнями сгенерированных файлов закоммичен. К заданию это не
относится, но правильнее добавить `.gitignore` со строкой `build/`. Если
спросят — «артефакты сборки не должны храниться в репозитории».

### 6.7. Случайность в тесте

`TestRange` — 100 итераций и проверка границ. Это корректно, но проверяет
только диапазон, а не распределение, и результат непредсказуем. Ответ:
«для рандомной функции нельзя проверять конкретное значение; проверяем
инвариант — результат всегда между `hypot` и `hypot + 10`».

## 7. Как выглядел проект на шагах 5.I и 5.II (уметь показать)

Итоговый код — это 5.V. Если попросят «покажи 5.I», нужен вариант без
шаблонов, где библиотека — настоящая статическая, а исходники рядом с main.

**Структура 5.I:**

```
5lesson/
├── CMakeLists.txt
├── main.cpp
├── hypotenuse.h
├── hypotenuse.cpp
├── hypotenuse_rand.h
└── hypotenuse_rand.cpp
```

`hypotenuse.h`:

```cpp
#pragma once
namespace my_lib { namespace usual {
double hypotenuse(int a, int b);
} }
```

`hypotenuse.cpp`:

```cpp
#include "hypotenuse.h"
#include <cmath>
namespace my_lib { namespace usual {
double hypotenuse(int a, int b) {
    return std::sqrt(static_cast<double>(a) * a + static_cast<double>(b) * b);
}
} }
```

`CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.14)
project(oop_5_1 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(mylib STATIC hypotenuse.cpp hypotenuse_rand.cpp)
target_include_directories(mylib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

add_executable(exec_trg main.cpp)
target_link_libraries(exec_trg PRIVATE mylib)
```

Проверено: собирается, создаёт `build/libmylib.a`, программа выводит две
гипотенузы.

**5.II** — те же четыре файла переезжают в `my_lib/`, туда же переносится
`add_library`/`target_include_directories` (в `my_lib/CMakeLists.txt`), а в
корне появляется `add_subdirectory(my_lib)`. Всё остальное не меняется.

**5.V** — тела функций переезжают в `.h` и становятся `template<typename T>`,
`.cpp` удаляются, `STATIC` меняется на `INTERFACE`.

## 8. Вопросы преподавателя и готовые ответы

1. **Что такое CMake и зачем он нужен?**
   Это система сборки (точнее, генератор систем сборки). Она читает
   `CMakeLists.txt` и создаёт Makefile/Ninja/Xcode-проект. Даёт
   кросс-платформенность и управление зависимостями; одна и та же
   конфигурация работает на macOS, Linux, Windows.
2. **Что делает `cmake -S . -B build`?**
   Конфигурирует проект: читает сценарии, проверяет компилятор, скачивает
   зависимости, генерирует файлы сборки в `build`. Код ещё не компилируется.
3. **Чем `cmake --build build` отличается от конфигурации?**
   Это уже сама компиляция и компоновка (вызывает make/ninja в `build`).
4. **Что такое цель (target)?**
   Именованный результат сборки: исполняемый файл, библиотека или
   «интерфейсная» цель без файлов. `exec_trg`, `mytst_exec`, `mylib` —
   цели.
5. **`add_library` с `STATIC`, `SHARED`, `INTERFACE` — в чём разница?**
   `STATIC` — архив `.a`, код вкомпилируется в программу при линковке.
   `SHARED` — динамическая библиотека `.so/.dylib`, загружается во время
   работы. `INTERFACE` — файлов нет, только требования использования
   (include-каталоги, определения). У вас `INTERFACE` из-за шаблонов в 5.V.
6. **Почему шаблоны должны быть в заголовке?**
   Компилятор создаёт конкретную версию функции для каждого `T` в месте
   вызова. Для этого ему нужно видеть тело шаблона. Если тело в `.cpp`,
   другая единица трансляции его не увидит → ошибка компоновки.
7. **Что такое `target_link_libraries`?**
   Подключение цели-зависимости. Для библиотеки — передать её компоновщику;
   для `INTERFACE` — унаследовать её требования (например, `-I` каталоги).
   Ключевые слова `PUBLIC/PRIVATE/INTERFACE` управляют тем, кому передаются
   эти требования.
8. **Почему тесты в другой папке видят `hypotenuse.h`?**
   Потому что `mylib` объявлена с `INTERFACE`-каталогом, и
   `target_link_libraries(mytst_exec PUBLIC mylib)` пробросил `-I.../my_lib`.
   Это видно в `build/tests/CMakeFiles/mytst_exec.dir/flags.make`.
9. **Что такое FetchContent?**
   Скачивание и подключение зависимости на этапе конфигурации. У нас —
   googletest по зафиксированному URL/коммиту, в `build/_deps`. Плюс: не надо
   ставить в систему, версия воспроизводима.
10. **Почему у тестов нет `main()`?**
    `GTest::gtest_main` предоставляет готовый `main()`, который запускает все
    зарегистрированные тесты.
11. **Что делает `gtest_discover_tests`?**
    На этапе сборки запускает тестовый бинарник с `--gtest_list_tests` и
    регистрирует каждый `TEST` отдельным тестом CTest, чтобы их можно было
    запускать/фильтровать по отдельности.
12. **Разница `EXPECT_` и `ASSERT_`?**
    `EXPECT` — некритичная проверка: сообщает об ошибке и идёт дальше.
    `ASSERT` — критичная: прерывает текущий тест (return), остальные строки
    не выполняются; другие тесты продолжаются.
13. **Покажите, что тест падает.**
    `AssertVsExpect` содержит намеренно неверные ожидания (`99.0`). Вывод:
    две ошибки (строки 17 и 21), после `ASSERT` строка 22 не выполнилась.
14. **Почему `ctest` показывает 4 теста, а файл один?**
    `gtest_discover_tests` зарегистрировал каждый `TEST` как отдельный тест
    CTest.
15. **Как выключить тесты?**
    `cmake -S . -B build -DBUILD_TESTS=OFF`. Тогда `if(BUILD_TESTS)` ложно,
    `add_subdirectory(tests)` не выполняется, gtest не скачивается и не
    собирается, цели `mytst_exec` нет.
16. **Что изменилось в 5.V?**
    Функции стали шаблонными (`template<typename T>`), тела переехали в
    заголовки, `.cpp` удалены, цель библиотеки — `INTERFACE`.
17. **Зачем `static_cast<double>`?**
    Чтобы умножение `int` не переполнилось и `sqrt` работал с вещественными
    числами. Иначе для больших `a`, `b` результат был бы неверным.
18. **Почему `static` у генератора случайных чисел?**
    Чтобы инициализировать (`random_device`) и создавать генератор один раз,
    а не на каждом вызове; состояние сохраняется между вызовами.
19. **Зачем пространства имён?**
    Чтобы две версии функции (`usual` и `randver`) не конфликтовали и чтобы
    имена библиотеки не пересекались с чужими. `my_lib` — пространство
    библиотеки, `usual`/`randver` — версии.
20. **Что будет, если убрать `#pragma once`?**
    При повторном включении заголовка в одну единицу трансляции будет
    повторное объявление/определение → ошибка компиляции.
21. **Почему `EXPECT_DOUBLE_EQ`, а не `EXPECT_EQ`?**
    Вещественные числа нельзя надёжно сравнивать на точное равенство из-за
    погрешности. `_DOUBLE_EQ` использует допуск (около 4 ULP); для явного
    допуска есть `EXPECT_NEAR`.
22. **Как запустить только один тест?**
    `ctest -R Имя` или `./build/tests/mytst_exec --gtest_filter=Набор.Имя`.
23. **Где физически лежит библиотека?**
    В итоговой версии — нигде: она header-only (`INTERFACE`). На шагах
    5.I/5.II — `build/libmylib.a` (статический архив).
24. **Почему `build` вне исходников?**
    Out-of-source build: артефакты не смешиваются с кодом, каталог можно
    удалить и пересобрать, разные конфигурации не конфликтуют.
25. **Что такое единица трансляции?**
    Один `.cpp` после работы препроцессора (со всеми вставленными `#include`),
    который компилируется в один объектный файл.
26. **Почему в `5.all.cpp` не пишется `<int>`?**
    Тип шаблона выводится из аргументов (`a`, `b` — `int`). Явное указание
    нужно, когда вывести нельзя или хочется другой тип.

## 9. Сценарий демонстрации на 3–4 минуты

1. **Структура.** Показать дерево: `main` + `my_lib/` + `tests/`, объяснить
   соответствие пунктам 5.I–5.V.
2. **Библиотека.** Открыть `my_lib/hypotenuse.h`: шаблон, `namespace
   my_lib::usual`, `static_cast<double>`, формула Пифагора. Затем
   `hypotenuse_rand.h`: `mt19937`, `uniform_int_distribution`, «монетка».
3. **CMake.** Корневой файл: стандарт C++17, `option(BUILD_TESTS)`,
   `add_subdirectory(my_lib)`, `add_executable`, `target_link_libraries`,
   `if(BUILD_TESTS)`.
4. **`my_lib/CMakeLists.txt`.** Объяснить `INTERFACE`: шаблоны → header-only,
   поэтому нет `.a`; include-каталог пробрасывается потребителям.
5. **Тесты.** `tests/CMakeLists.txt`: `FetchContent` (скачивает gtest),
   `GTest::gtest_main` (даёт `main`), `gtest_discover_tests` (каждый `TEST` —
   отдельный тест CTest).
6. **Чистая сборка.**
   ```bash
   rm -rf build
   cmake -S . -B build
   cmake --build build
   ctest --test-dir build/tests --output-on-failure
   ```
   Показать 3 зелёных и 1 намеренно красный.
7. **ASSERT vs EXPECT.** Показать вывод: две ошибки (строки 17 и 21), строка
   22 не выполнилась после `ASSERT`.
8. **Зелёный прогон.** `ctest --test-dir build/tests -E AssertVsExpect` →
   100 %.
9. **5.IV.** `cmake -S . -B build-no-tests -DBUILD_TESTS=OFF` и
   `cmake --build build-no-tests`; показать, что gtest и `mytst_exec` не
   появились.
10. **Программа.** `echo "3 4" | ./build/exec_trg` → два числа: 5 и 5..15.

## 10. Мини-словарь

| Термин | Значение |
|---|---|
| Трансляция | Компиляция одного `.cpp` со всеми включёнными заголовками |
| Объявление / определение | «Функция есть, вот сигнатура» / «вот её тело» |
| Компоновка (link) | Сборка объектных файлов и библиотек в исполняемый файл |
| Статическая библиотека | Архив `.a`/`.lib`; код попадает в программу при линковке |
| Header-only | Вся реализация в заголовках, отдельного бинарного файла нет |
| Шаблон | Заготовка функции/класса, конкретизируется для типа `T` |
| Инстанцирование | Создание конкретной версии шаблона для типа |
| Usage requirements | Требования цели, передаваемые потребителям (`-I`, `-D`, флаги) |
| `PUBLIC`/`PRIVATE`/`INTERFACE` | Кому передавать требования: всем / только себе / только потребителям |
| CTest | Система запуска тестов в составе CMake |
| Фикстура/набор | Группа тестов (`TEST` suite) |
